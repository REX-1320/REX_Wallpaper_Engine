# Architecture Decision Records: ADR-001 through ADR-006

Format per ADR: Context → Decision → Consequences → Alternatives Considered.
Once accepted, an ADR is only reversed by a new ADR that explicitly supersedes it.

------------------------------------------------------------------------

## ADR-001: Core/Shell Language Split

**Status:** Accepted

**Context:** REX has performance-critical rendering/compositing work and
UI/business-logic work with very different iteration-speed needs. Solo dev,
AI-assisted (opencode).

**Decision:** Split the system in two:
- **Core** (WorkerW host, GPU compositor, animation engine, IPC server): **C++20**, MSVC toolchain, Direct3D 12.
- **Shell** (settings UI, widget host manager, SDK surface, marketplace client, automation engine, event bus): **C#/.NET 8**, WinUI 3.
- **Widget authoring layer:** TypeScript/JavaScript, executed in an isolated V8 runtime per widget process.

**Consequences:**
- Two build systems (CMake for core, MSBuild/dotnet for shell) — accepted overhead.
- Requires a stable IPC contract (see ADR-002) — becomes the system's most important interface.
- Core is small (~10–15k LOC target) and changes rarely once stable; shell is large (~60–80k LOC) and iterates constantly.
- AI-assisted development is strongest in C#/TS, weakest in C++ — mitigated by keeping C++ surface area minimal and manually reviewing all of it.

**Alternatives considered:** All-C++ (rejected: iteration speed too slow for solo dev); All-C# with P/Invoke to GPU (rejected: GC pauses risk frame drops once widget count scales, deferred perf cliff to Phase 3); Electron shell (rejected: weight/perf contradicts product thesis); Rust core (deferred — see ADR-006).

## ADR-002: Inter-Process Communication (IPC) Protocol

**Status:** Accepted

**Context:** Core and Shell run as separate processes (this is also required for
crash isolation — a core crash shouldn't necessarily require killing the settings UI
and vice versa). They must exchange structured messages with low latency (widget
position updates, frame events, commands) and support request/response plus
fire-and-forget patterns.

**Decision:** **Named pipes** (`\\.\pipe\rex-core-shell`) carrying **length-prefixed
Protocol Buffers (protobuf)** messages. One duplex pipe for control messages
(commands, acks), a separate high-frequency pipe for frame/telemetry events to avoid
head-of-line blocking.

**Message envelope:**
```protobuf
message Envelope {
  uint64 id = 1;
  uint32 type = 2;        // maps to a registered message type
  bytes payload = 3;      // the actual typed message, protobuf-encoded
  uint64 timestamp_ms = 4;
}
```

**Consequences:**
- Protobuf requires a schema file (`.proto`) as the single source of truth for the
  IPC contract — this *is* the "stable API" boundary from the vision doc, made literal.
- Both C++ and C# have mature protobuf codegen (protobuf.js not needed; native libs exist for both).
- Named pipes are local-machine-only by design — acceptable, REX has no multi-machine use case.
- Two pipes (control + high-frequency) adds complexity but prevents a burst of frame events from delaying a critical shutdown command.

**Alternatives considered:** gRPC (rejected: gRPC-over-named-pipes on Windows is non-trivial, HTTP/2 overhead unnecessary for local IPC); raw JSON over pipes (rejected: slower serialization, no schema enforcement, harder to catch breaking changes at compile time); shared memory ring buffer (deferred — candidate optimization for the high-frequency channel post-Phase-3 if profiling shows pipe overhead matters).

## ADR-003: Plugin/Widget Sandboxing Model

**Status:** Accepted

**Context:** Third-party widget/plugin code must not be able to crash the desktop,
read arbitrary files, exfiltrate data, or consume unbounded CPU/memory. This is the
highest reputational-risk area of the whole project (see Vision §9).

**Decision:** Each widget instance runs in its **own OS process** (`rex-widget-host.exe`),
hosting an embedded V8 isolate (via a minimal embedding, not full Node.js — see
RES-SDK-Marketplace for embedding choice). Communication with the Shell is via the
same IPC mechanism as ADR-002, over a per-widget pipe. Each widget process is:
- Spawned with a **restricted job object** (Windows Job Objects) capping CPU time and
  working-set memory.
- Denied filesystem access by default except a per-widget sandboxed storage directory.
- Denied network access by default unless the manifest declares and the user grants it.
- Killed and restarted automatically if it exceeds its frame-time budget repeatedly (see RES-Testing-Security-Performance §Performance SLAs).

**Consequences:**
- One process per widget has memory overhead (~5–10MB baseline per V8 isolate) —
  acceptable trade for crash isolation; revisit if users routinely run 100+ widgets.
- Widget crashes are visible to the Shell (pipe disconnect) and recoverable without
  restarting REX itself.
- This is the *load-bearing* decision for Phase 5 (marketplace) even though it's
  implemented in Phase 2 — cannot be retrofitted cheaply, must be right from first
  plugin execution.

**Alternatives considered:** In-process scripting (rejected: one bad widget can crash
the whole shell — unacceptable given marketplace ambitions); WASM sandboxing instead
of V8/JS (deferred — genuinely promising for Phase 5+, revisit once a11y of authoring
web-native widgets is validated with real community members); Docker/container-based
isolation (rejected: too heavy for a desktop customization tool, poor Windows-native fit).

## ADR-004: Data Persistence & Serialization Format

**Status:** Accepted

**Context:** REX persists widget layouts, desktop profiles, automation flows, and
user settings. Needs to be human-diffable (for backup/restore, version control by
power users), fast to parse, and forward-compatible as the schema evolves.

**Decision:** **JSON** for all user-facing persisted state (profiles, widget configs,
automation flows), stored under `%LOCALAPPDATA%\REXTools\`. Each top-level document
carries a `schemaVersion` integer. Migrations are explicit, versioned functions
(`MigrateV1ToV2`, etc.) run on load — never silent/implicit upgrades.

**Consequences:**
- JSON is slower to parse than a binary format but negligible at REX's data sizes
  (profiles are KBs, not MBs).
- Human-readable format enables power-user editing and Git-based profile version
  control — a feature, not just an implementation detail.
- Requires discipline: every schema change needs a migration function and a test
  fixture of the "old" format — this is a testing-strategy commitment, not just a format choice.

**Alternatives considered:** Binary format (MessagePack/protobuf) for persistence
(rejected: loses human-readability/diffability which power users of this product
category specifically value — see Rainmeter's INI-editing culture); SQLite
(deferred: reconsider once profile counts or automation-history volume make
file-based JSON slow — not expected before Phase 4+).

## ADR-005: Telemetry & Crash Reporting

**Status:** Accepted

**Context:** A solo dev has no QA team; telemetry is the primary mechanism for
discovering bugs across the install base. Must be privacy-respecting and opt-in
per Vision §5/§12.

**Decision:** **Opt-in only, disabled by default**, surfaced clearly on first run
(not buried in settings). Collects: crash stack traces (with a local symbol
server, no PII), aggregate frame-time/memory stats, feature-usage counters (which
modules are enabled, not user content). Transport: batched HTTPS POST to a
lightweight self-hosted endpoint (not a third-party SDK, to avoid an extra
dependency/cost for a project with no revenue yet).

**Consequences:**
- Requires building a minimal ingestion backend before Phase 1 telemetry can be
  useful — small scope (accept JSON blob, write to a queryable store), but real work.
- No telemetry data before opt-in means Phase 0 debugging relies entirely on your
  own dogfooding — accepted, matches Phase 1 exit criteria ("you personally use it daily").

**Alternatives considered:** Third-party crash SDK (e.g., Sentry) (viable
alternative if self-hosting becomes a maintenance burden — revisit if backend
upkeep competes with feature work); always-on telemetry (rejected outright — conflicts
with product values and user trust, non-negotiable).

## ADR-006: Core Language — C++ Now, Rust Deferred

**Status:** Accepted (with a scheduled re-evaluation point)

**Context:** Rust offers memory safety without GC and would eliminate a class of
core-process bugs, but has a steeper simultaneous learning curve alongside
Windows/GPU/IPC work, and thinner Windows-native tooling/examples than C++ as of
this writing.

**Decision:** Build the Phase 0–3 core in **C++20**. Because ADR-002's IPC boundary
is language-agnostic (protobuf over named pipes), the core can be **rewritten in
Rust later without touching the Shell** if/when: (a) core stabilizes and stops
changing weekly, and (b) memory-safety bugs in the core prove costly enough to
justify the rewrite.

**Consequences:**
- Explicit debt marker: this ADR should be revisited at the **Phase 3 exit
  criteria checkpoint** — not left implicit.
- Core surface area is kept deliberately small (ADR-001) specifically so this
  rewrite stays feasible if chosen later.

**Alternatives considered:** Rust from day one (deferred, not rejected — the
IPC boundary makes this a reversible decision rather than a one-way door, which is
why C++ is acceptable now).
