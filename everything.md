## What REX is

A modern desktop personalization platform for Windows 10/11 — the layer between Windows and the user that Windows never built:

- **Widgets** — live info on the desktop (clock, weather, system monitor)
- **Wallpaper** — image, video, web, shader, scene, audio-reactive
- **WindowFX / Personalization** — taskbar, explorer, start menu, blur/acrylic/mica
- **Automation** — event-driven workflows (planned)
- **SDK + Marketplace** — build/share widgets and content (planned)

Competitor space: Rainmeter + Wallpaper Engine + StartAllBack + Seelen UI, unified in one product.

## Architecture & stack

```
Core (C++20)  ←── IPC: named pipes + protobuf ──→  Shell/UI
  • WorkerW host (behind desktop icons)             • Electron + React (current)
  • D3D12 compositor + render thread                • C# WinUI/XAML (rex-shell, parallel)
  • Wallpaper renderers (6 kinds)                   • TS Surface System (design framework)
  • Module system (load/lifecycle/health)
  • Desktop personalization adapters (registry)
```

## DONE already ✅

### Wallpaper engine (the most mature area)

- **6 renderers:** Image, Video (MF + ffmpeg), Web, Shader (D3D12 root sig + PSO + HLSL), Scene (ECS + RenderPipeline), Audio visualizer (WASAPI + FFT)
- **Decoders/loaders:** MediaFoundationDecoder, WICTextureLoader, ImageLoader, SceneLoader
- **Playback:** play/pause/stop, seek, loop, speed, brightness/contrast/saturation, volume, audio-reactive, fill mode
- **Telemetry:** frames decoded/dropped, FPS, latency (`PlaybackTelemetry`)
- **Multi-monitor:** independent per-monitor assignment, display-change detection
- **Engine:** LoadScene/UnloadScene, background render thread, D3D12 compositor, recovery (`ReinitializeCompositor`)
- **Shader pipeline:** D3D12 root signature + PSO + HLSL compilation
- **Video-pool VRAM (2026-10-19):** every 4K video session used to pin another pool of dedicated VRAM (**+180 MiB** P010 4K / **+205 MiB** SW BGRA per apply). Root cause proven with two probes: the AMD driver charges a **per-import pin** — each D3D12 `OpenSharedHandle` of the decoder's shared textures that is then used on the GPU stays resident until process exit (`Trim`, releasing imports, releasing textures and destroying both devices are all no-ops; +180 per import+use cycle, measured 183.8→727 MiB; import without GPU use *is* Trim-freed). Fix: the decoder keeps its pool generation across `Close()` (`ReleasePool()` only in the destructor, `EnsurePool` device guard) and the controller reuses the closed decoder (same NT handles); `D3D12Renderer::ClearVideoFrame()` keeps its import cache (LRU evicts a new generation, `Shutdown` releases); and an image apply deliberately stops the runtime because process exit is the only reclaim boundary. **Live:** 6 alternating same-surface applies **flat at 918.9 MB, only 2 pool builds in the log**; video→image **0 MB** with the image still drawn by the OS; cold video respawn 865 ms. Idle-timer idea rejected (stop-on-image is immediate). Reverted as ineffective: decoder `ClearState/Flush`, renderer null-SRV overwrite, `IDXGIDevice3::Trim`. **Follow-up (alternating pool *formats*) closed 2026-10-29** — see *Pool-generation cache* below.
- **Recent (git):** ffmpeg video pipeline, D3D12 renderer work, shutdown-crash fixes (`4ba29fa`, `1ca6195`)

### Pool-generation cache — alternating formats no longer re-pin VRAM (2026-10-29)

- **Retraction first.** The P2 claim that a long-lived runtime degrades to **40 % 3D** after many clip/format switches **does not reproduce**. A-B-A on the same clip: clean engine **27.90 %** → same process after 12 SDR↔HDR switches **28.72 %** → fresh process **27.73 %**. The 40.31 % reading in `paiint_hw_usage_2026-10-28_rendering_2.csv` (§6 T4) was session noise; `test.md` §6/§7 now say so. Ruled out while looking: swapchain duplication, scene/ECS accumulation (`scenesLoaded=23`, `scenesReleased=22`), copy-engine chain (`gpu_other_pct=0`), shared-memory spill, COM holders (`refMin=refMax=2`).
- **The real defect.** Dedicated VRAM (WDDM per-process counter) grew **963.7 → 3,099.8 MB** across 12 alternating SDR↔HDR format switches while the engine's own `gpuDedicated` stayed at **1,017,614,336 B** — blind to ~2.1 GB. A harness isolated the variable: 10 same-format re-applies were flat (510–565 MB), each format switch cost **+264 MB** (442.6 → 2,366.8 MB), and 60 s idle released nothing. Root cause: a format change rebuilt the D3D11 pool → new NT handles → a new D3D12 import generation → another permanent per-import pin (the AMD behaviour already documented for the 2026-10-19 fix).
- **Fix.** Decoder: bounded pool-generation cache keyed by `(width, height, format)` — `kMaxLivePoolGenerations = 3` live generations, LRU-retired, handles closed on eviction/teardown (`ReuseCachedPool` / `RetireActivePool` / `TrimPoolCache`, generation stamped into `VideoFrame::poolGeneration`). Renderer: slot cache keyed by `(sharedHandle, poolGeneration)` (NT handle values are recycled, so the handle alone cannot identify an import), `kMaxVideoSlots = 24` = 8 slots × 3 generations. Header pins the SRV-heap contract: `kSrvHeapSize = 128`, `kToneStatsUavBase = 64`, with `static_assert`s.
- **Second bug found while fixing it — device removal.** The tone-stats peak-detection UAVs were hard-coded at descriptor **20**, but 24 video slots span descriptors **1..48**; `CreateShaderResourceView` overwrote the UAVs and the dispatch faulted the GPU (`DXGI_ERROR_DEVICE_HUNG`, `Present FAILED 0x887a0005`, reason `0x887a0006`, up to 10 removals in one run). A/B proved it: decoder reuse + renderer evict-on-generation-change → **0 removals**; decoder reuse + retained imports on the old layout → **10**. With the heap contract fixed: **0 removals** in every subsequent run. Also fixed: `m_inputFormat` was only set on the re-import branch, so a cached HDR slot would have shaded with SDR constants (now read from the bound resource's format on both paths).
- **User-visible payoff — the HDR "red channel only" bug is fixed (verified 2026-10-29).** The 2020 LG OLED HDR10 clip used to present a red-only image (`meanR 41.4 / meanG 3.9 / meanB 3.0`, **29.2 %** red-dominant) because the UAV/SRV collision zeroed the chroma SRVs of the second pool generation — luma valid + CbCr = 0 collapses BT.2020 YCbCr→RGB to `(Y, ~0, ~0)` — and the stale `m_inputFormat` could shade a cached NV12 generation with P010 constants. Re-measured on the exact defect path (SDR NV12 gen 1 → HDR P010 gen 2 in one runtime): **`18.7 / 22.0 / 22.7`, 0 % red-dominant**, green mint leaves and neutral glass, matching the source frame (`22.8 / 23.9 / 24.7`); a fresh HDR open reads `18.9 / 22.2 / 22.9`, and the SDR control clip still renders correctly (`41.0 / 23.6 / 13.1`). **Re-run on the shipped runtime** (`FB7AD253…F35D660B`, hash-identical inside the rebuilt MSIX): `18.8 / 22.1 / 22.8`, 0 % red-dominant, no device removal. Evidence: `%TEMP%\opencode\color3-switch.jpg` + `color3-switch.log`.
- **Verified.** 10 loads / 5 SDR↔HDR cycles: **774 MB (SDR gen 1) ↔ 1,167 MB (HDR gen 2), perfectly flat**, end 825.9 MB, peak 1,167.5 MB, `rebuilt=2 reused=9 slotEvict=0 removed=0 imports=16`. Pre-fix baseline: peak **2,102.8 MB**, end 1,760–1,808 MB, **+130 MB per load**. Three further 8-pair stress runs (48 loads / 24 switches) reproduced the same shape: `rebuilt=2 reused=15 removed=0` each. Unit test `DecoderPoolCacheTest.FindsMatchingGenerationAndLruVictim`; `DecoderPool*` 10/10 green.
- **Artefacts rebuilt (2026-10-29, carrying the fix).** Portable `app\dist-exe\Paiint-0.1.0-2026-10-29.exe` — **108,085,074 B**, SHA256 `6DCE66FCE701AC27F4370F1E5BD0C3A404553FC60139C1D3D5C0D4ACBCEA507C`; Store MSIX `packaging\msix\out\Paiint-0.1.0-x64.msix` — **183,389,793 B (174.9 MB)**, SHA256 `42ADC8BAA253244995622E33CD0A99882A535F23BACFD1FF758F312574E36271`, built with the Store identity (`Moinu.Paiint`, `CN=9D8DC345-…`, unsigned — Microsoft signs it). `resources\bin\paiint-wallpaper-runtime.exe` in the MSIX stage **and** in `app\dist-exe\win-unpacked` is hash-identical to `rex-core\build\Release\paiint-wallpaper-runtime.exe` (`FB7AD2538E64D8B857B509FA94489271C1E32D3C30EED278AAAD287EF35D660B`), so both payloads carry the descriptor-layout fix rather than a stale runtime. ### Quit-time snapshot — the last frame stays on the desktop (2026-10-26)

> **Format superseded 2026-10-28:** the snapshot is a **JPEG** (`last-frame.jpg`) now — see *Instant quit, close-to-quit and the Paiint sidebar mark* below. The PNG file names, sizes and timings in this section describe the 2026-10-26/27 builds.

- **What it does.** Quitting Paiint no longer snaps the desktop back to a stale image: the runtime captures the frame that is on screen, JPEG-encodes it to `%USERPROFILE%\Pictures\Paiint\last-frame.jpg` (the real Pictures known folder since 2026-10-27 — it used to be `%LOCALAPPDATA%\Paiint\last-frame.png`, which MSIX virtualises and uninstall can orphan; the file was a PNG until 2026-10-28), applies it through the native Windows wallpaper API (`SetImageWallpaper` → `IDesktopWallpaper::SetWallpaper` when packaged, legacy `SystemParametersInfoW(SPI_SETDESKWALLPAPER)` otherwise, `Fill`), and only then tears WorkerW down. That is Wallpaper Engine's "leave the last frame" behaviour, done by handing the final pixels to the OS rather than by keeping a compositor alive.
- **The quit drain (P0, fixed 2026-10-27).** `will-quit` used to send `SHUTDOWN {snapshot:true}` and return, so Electron finished its teardown and killed the child process while the render thread was still capturing — the quit ended abruptly instead of waiting for the runtime's `Wallpaper runtime shutdown complete`, and the snapshot could be stale or missing. `wallpaperRuntime.stop()` now returns a Promise resolved by the runtime's `exit` event or a bounded deadline (15 s snapshot / 5 s plain), and `will-quit` calls `event.preventDefault()`, awaits it, then re-quits. Two details make the re-entry safe: the re-quit is a `setImmediate` macrotask (a resolved `stop()` settles as a microtask *inside* the emission, where a re-entrant `app.quit()` can be swallowed), and a `quitDrainFinished` flag lets the second `will-quit` pass through while a second quit during the drain keeps waiting instead of killing the capture. The pre-drain cleanup is wrapped so a throw cannot leave the quit prevented with nothing scheduled. **Live:** three closes took 1.6–3.3 s, each wrote a fresh 3840×2160 PNG, runtime exit 0, log ended `app: runtime drained, quitting` → `Wallpaper runtime shutdown complete`; a close with **no runtime process** (the still-image path) also exited cleanly, leaving no windowless process behind.
- **Opt-in, not automatic.** The capture only runs for `SHUTDOWN {snapshot:true}`, which Electron sends from `will-quit`. The idle reclaim that stops the runtime after an image apply sends a plain `SHUTDOWN`, so switching to a still image can never be overwritten by an old video frame. Verified by hash: an image apply + plain shutdown left the snapshot file byte-identical.
- **Root cause of the first failure (worth remembering).** The capture originally allocated a READBACK-heap *texture* as its copy target and got `E_INVALIDARG` (`0x80070057`) at every size and format. A standalone repro proved the rule: D3D12 allows **only buffers** on `UPLOAD`/`READBACK` heaps — there are no D3D11-style staging textures. Default-heap textures created fine; upload/readback textures failed; readback buffers succeeded. The fix is the canonical path: `GetCopyableFootprints` → READBACK **buffer** → `CopyTextureRegion` → `Map`, walking rows by the 256-byte-aligned `RowPitch` (15360 at 4K, not `width*4`). The old code would also have read the buffer as tightly packed, so this was two bugs in one line of design.
- **HDR and thread ownership.** The capture runs on the render thread (the owner of `D3D12Renderer`) via a queued request from `Engine::CaptureFrame`; `BeginFrameLocked`/`EndFrameLocked` let it hold `m_renderMutex` across setup plus exactly one frame. On an HDR display it forces the SDR pipeline for that frame (`SetForceSdr(true)` + `SyncHdrStateLocked`), so the PNG carries the same mpv-parity tone map the SDR desktop sees instead of a PQ buffer. Deliberately not restored — this only runs on the way out. The narrowing understands exactly the two SDR back-buffer formats (`R10G10B10A2_UNORM`, `R8G8B8A8_UNORM`); any other format (in practice FP16, i.e. the HDR switch did not take) is refused with a log line rather than decoded as 8-bit RGBA — a wrong-format capture would become a sticky garbage wallpaper, so the capture refuses instead of guessing.
- **Crash safety (PNG era).** The PNG was encoded to `last-frame.png.tmp` and renamed with `MOVEFILE_WRITE_THROUGH`, because Windows re-reads the wallpaper path at sign-in: a kill mid-encode must not leave a truncated file behind. The Electron quit fallback is 15 s for snapshot quits (5 s otherwise) — the first capture on a 4K desktop measured ~4 s end to end because `SystemParametersInfo` broadcasts a synchronous `WM_SETTINGCHANGE` that waits for Explorer to load the new image.
- **Verified live (2026-10-26).** `3840x2160` PNG, 207,971 B, valid signature, sampled luma 0–255 (mean 127.8 — real picture, not black); `HKCU\Control Panel\Desktop\Wallpaper` points at the file; quit 1.2 s once the wallpaper was already cached. Native suite **824/824**, app suite **76/76**. The false `VEH exception 0x71A` that every quit used to append to `%TEMP%\Paiint\crash.log` is also fixed: the VEH now ignores that one benign WTS/RPC code once a deliberate teardown has begun (`g_teardownStarted`), and a snapshot quit left `crash.log` unchanged at 420 lines.

### Playlist scoping, Stop, snapshot toggle and verified recovery (2026-10-26)

- **Playlist rules no longer leak onto non-members (P0).** `buildRotationPlan()` and `fireChange()` resolved the active playlist through `state.lastAppliedPath`, which only the playlist engine wrote — a manual gallery apply never touched it, so applying a non-member file while a playlist was live left the old playlist's Timer/scene-end rules running over it. The new pure resolver `app/src/wallpapers/playlist/scope.js` makes the store's **applied record** authoritative (`appliedWallpaper` → `playlistFor`), uses `lastAppliedPath` only when no applied record exists (boot), and returns `NO_PLAYLIST` for a non-member; `buildRotationPlan()` maps that to `null` (stop the plan). 8 unit cases in `scope.test.js`. **Live:** with a Nature plan live (queue 2), double-clicking non-member `black-myth-wukong-moewalls-com.mp4` cleared main's scheduler (`playlistId/playlistName/mode` null) and `getLastApplied` reported the new file.

### MSIX lifecycle — stills, snapshot path, launch at login (2026-10-27)

The three things a packaged app could not do like the portable build: write a wallpaper path Explorer will read, leave the snapshot somewhere Explorer can reach, and register itself for logon.

- **Still images go through `IDesktopWallpaper` when packaged (P0).** `SetImageWallpaper` used to write `HKCU\Control Panel\Desktop\Wallpaper` and call `SystemParametersInfoW(SPI_SETDESKWALLPAPER)`. MSIX redirects every HKCU write into the package's private hive, so Explorer never saw the value. It now calls `IDesktopWallpaper::SetWallpaper(NULL, path)` — shell COM, unvirtualized, `NULL` = all monitors — and maps our fit modes to `DESKTOP_WALLPAPER_POSITION` (`Fill`/`Fit`/`Stretch`/`Tile`/`Center`/`Span`). - **The snapshot lives in Pictures, not AppData (P0).** MSIX redirects `%LOCALAPPDATA%` to `%LOCALAPPDATA%\Packages\<PFN>\LocalCache`, so a snapshot written there is invisible to Explorer and would be deleted with the package while still being the live wallpaper. `LastFrameImagePath()` now resolves `SHGetKnownFolderPath(FOLDERID_Pictures)` → `Pictures\Paiint\last-frame.jpg` (the file was a PNG until 2026-10-28), and Electron's `lastFrameSnapshotPath()` mirrors it with `app.getPath('pictures')` so both sides agree even if the user moved their Pictures folder. **Dev verified (PNG era, 2026-10-27):** a quit wrote `C:\Users\Moinu\Pictures\Paiint\last-frame.png` (3840×2160, valid PNG), the desktop kept it, and the stale `%LOCALAPPDATA%` copy was left untouched.
- **Launch at login is a manifest startup task, not a Run key (P1).** MSIX redirects `app.setLoginItemSettings`'s HKCU Run write into the package hive, so the old checkbox was a silent no-op. `packaging/msix/AppxManifest.xml` now declares `desktop:Extension Category="windows.startupTask"` (`TaskId="PaiintStartup"`, `Enabled="false"`, `DisplayName="Paiint"`, `Executable="resources\bin\paiint-startup.exe"`) and adds `desktop` to `IgnorableNamespaces`. `Enabled="false"` matches the portable default: the app requests the task on first run, and a user who disables it in Task Manager cannot be silently re-enabled.
- **The startup stub is the only process that can toggle the task.** A packaged app cannot call `Windows.ApplicationModel.StartupTask` for itself from a plain child process, and the documented startupTask form launches its executable with no arguments (`uap10:Parameters` exists in the schema but is undocumented for startupTask, so the logon path does not bet on it). `rex-core/tools/StartupStub.cpp` builds `paiint-startup.exe` (WIN32 GUI subsystem, no console flash): a bare launch starts `Paiint.exe --startup-task`; `--status` / `--enable` / `--disable` drive the task and print one token — `enabled`, `disabled`, `disabled-by-user`, `disabled-by-policy`, `enabled-by-policy`, `unpackaged`, `error` — with a trace in `%TEMP%\paiint-startup.log`. `app/electron/startup-task.cjs` parses that (`unpackaged` or a missing stub → `null`, i.e. no package identity, use the Run key; a stub that exists but never answers → `unavailable`, logged loudly instead of silently masquerading as portable) and is covered by 6 tests. The answer is cached for 10 s and every write refreshes it, so a tray menu rebuild never blocks on a child process. `--enable` treats `enabled-by-policy` as success, and `--disable` re-reads the task state instead of claiming success when policy still owns it.
- **Electron picks the right mechanism per build.** `applyLoginItem()` asks the helper first and only falls back to `app.setLoginItemSettings` when it reports `unpackaged`; `loginItemEnabled()` reads the task state (so a Task-Manager veto shows as off) and falls back to `launchItems` for the Run key. `--startup-task` launches read the **live** `startup.startMinimized`: tray + wallpaper with no window when true, a normal window when false. The first-run registration is deferred with `setImmediate` so the helper's spawn cannot delay the window or the wallpaper.

### Playlist stills — a scene-end mode no longer parks on an image (2026-10-25)

- **The bug.** `After Current Ends` / `Video Ends` / `Audio Ends` advanced only on the native `ENDED` event. A still image never emits one, so the first time the rotation reached an image it stopped dead: `currentPath` = the image, `nextDueAt: null`, ten members behind it never played. Found live on 2026-10-24, with the desktop left sitting on `REX_rowpitch_test_1366x768.png`.
- **The fix (product decision: stills get a dwell time).** `app/electron/playlist-scheduler.cjs` arms a 30 s dwell whenever a scene-end mode is on a still — both when a plan arrives (`_applyDwellPlan`) and when the rotation lands on one (`_armDwell` inside `_advance`). A still is identified by `apply.kind === 'image'`, the same field `main.cjs` dispatches on, with an extension fallback for older plans. The dwell is keyed by playlist + mode + path, so the renderer's frequent plan rebroadcasts do **not** restart the clock (otherwise the image would dwell forever — the same stall in a new costume). Advancing to a video cancels it, and `Timer` mode is untouched. The duration is overridable per plan (`plan.imageDwellMs`) and per scheduler (constructor), so the playlist dialog can expose it later without another engine change.
- **Verified.** 17/17 scheduler tests (4 new: the dwell fires, a rebroadcast does not restart it, landing on an image arms it, the value is configurable and never applies to Timer), full app suite 76/76, `pnpm lint` 0 errors, `pnpm typecheck` 0. **Live on `Paiint-0.1.0-2026-10-25-d.exe`:** boot restored the rotation parked on the test image, logged `image dwell due in 30000ms`, a plan rebroadcast 175 ms later logged `due in 29825ms` (clock preserved), and 30 s later it applied `marvel-spiderman-miles-morales.1920x1080.mp4` with `reason=After Current Ends` — the desktop unstuck itself.

### Inspector usage research (2026-10-21)

### Renderer watchdog - false "stale" reloads while occluded (2026-10-23)

The renderer appeared to stall for 16-19 s and the supervisor reloaded it every ~75 s (`renderer stale 16s - reloading`), with one reload ending as `renderer gone (crashed) exitCode -1` (tracking: the P1 entry in `TODO.md`). The open diagnosis blamed the gallery's poster decodes; that was wrong.

- **The restore is not the blocker.** Replaying the real built gallery against the user's library (35 entries, 34 persisted posters) produced **33 tiles, 32 posters, 0 long tasks and a 2.04 s maximum heartbeat gap**. The HEVC `fallback-thumbnail ... media-error` log lines appear ~2.2 s **after** each reload, i.e. they are the restored gallery retrying, not the cause.
- **Root cause: a throttled page timer in an occluded window.** The 2 s `renderer:ping` is a page timer (`preload.cjs:109-115`), and `Supervisor._rendererTick` only skips hidden/minimized windows (`supervisor/supervisor.cjs:198-200`). A window fully covered by another app still reports `win.isVisible() === true`, but Chromium marks the page `visibilityState:"hidden"` and throttles its timers. The occlusion probe measured the 2 s cadence becoming 3 s immediately, and Chromium's intensive throttling (after ~5 minutes hidden) drops page timers to about once a minute - producing 60 s+ heartbeat gaps, a 16-19 s stale reading and the ~75 s reload loop. The first stall 6m43s after launch matches the 5-minute delay, and the loop stopped when the window came back to the foreground.
- **Fix A - make the watchdog ask the renderer.** `main.cjs` + `preload.cjs` add a main-initiated `renderer:probe` / `renderer:probe-reply` round trip. When the heartbeat is stale, `_rendererTick` calls `probeRenderer` (2.5 s timeout) and re-baselines if the renderer answers; only a failed probe reloads. Main -> renderer IPC is not subject to page-timer throttling, so an occluded-but-healthy renderer is no longer killed, while a genuinely blocked main thread (which cannot answer) still is. The 15 s threshold and the 2 s heartbeat are unchanged. `backgroundThrottling:false` (already added by the in-flight scheduler work) is kept and its comment now explains the watchdog case too; the logged build predates that switch.
- **Fix B - restore hardening.** `WallpaperGallery.jsx` gives the persisted-poster probe a 1.5 s timeout (previously a slow/offline library path could wedge the restore forever), yields a macrotask between restore entries and before the poster loop, and decodes one poster at a time. Persisted thumbnails are still preferred, imports are untouched, and the GPU-worker fallback for files Chromium cannot decode is unchanged.
- **Verification.** Supervisor logic probe: stale + probe answers -> 0 reloads and the clock is re-baselined; stale + probe fails -> 1 reload; fresh heartbeat -> no probe; no probe wiring -> 1 reload (the old behaviour). Rebuilt `dist` restore: 33 tiles, 32 posters, 31 probe images loaded, 0 image errors, 0 long tasks, 2.04 s max heartbeat gap. `pnpm lint` exit 0 (pre-existing warnings only), `pnpm typecheck` exit 0, `pnpm build` exit 0.
- **Files:** `app/electron/main.cjs`, `app/electron/preload.cjs`, `app/electron/supervisor/supervisor.cjs`, `app/src/wallpapers/WallpaperGallery.jsx`.

### Video output research — players, tone mapping, decoding, verification (2026-10-19)

Full sourced record: [`research-video.md`](research-video.md) (four read-only tracks: A players/renderers · B HDR→SDR tone mapping · C decoding & color pipeline · D verification + wallpaper prior art; sources = upstream code, ITU-R reports, Microsoft Learn, Doom9/AVS/community). Commissioned to answer *"which is the best video output player (VLC among them), everything about video decoding, and how do we confirm the file == the wallpaper"* after the engine's HDR path was measured darker/crushed vs VLC 3.0.23 on the Spider-Man DV-P8.1 clip ("too much black").

**Verdict — VLC is good-but-dated, not the ceiling.** VLC 3.x's Windows D3D11 HDR→SDR path is *one* fixed Hable curve (`hable(L·0.01)/hable(11.2)`) with a fixed 100-nit reference, no metadata, no black-point handling, no dithering, no controls (source-verified; the `0.01` matches our measurement). VLC 4.0 (**unreleased**) replaced it with libplacebo; its ©2024 D3D11 tone-map module is SDR→**HDR**, not a better HDR→SDR. Quality leaders: **madVR** (DTM reference; public renderer frozen 2018, HDR test builds continue) and **mpv/libplacebo gpu-next** (best maintained open stack: spline/BT.2390, BT.1886 black-point compensation, peak detection, blue-noise dithering); **MPC-VR** (BT2390 + friends, 125-nit SDR default) is the best free DirectShow option. Ranking: **madVR ≳ libplacebo > MPC-VR > VLC 3.x D3D11 > Kodi/PotPlayer > MF/EVR/WMP**.

**Verification (how to actually prove "file == wallpaper").** Three references, used deliberately: the *file + trusted decode chain* (numerical), a *reference player* (subjective), the *standards* (policy). ### mpv parity — libplacebo v7.360.0 reverse-engineered and numerically validated (2026-10-20)
**Decision.** The user picked **mpv** as the HDR→SDR ground truth (not BT.2390, not VLC). mpv 0.41.0 (libplacebo **v7.360.0**, FFmpeg N-123099) was installed system-wide (`winget shinchiro.mpv`, user PATH) and is the reference the engine must match. (The newer daily build, libplacebo v7.377, was rejected: it adds dynamic-target dimming and a hyperbolic spline that the installed build does **not** have.)
**The whole mpv pipeline is now known from source and validated numerically** (libplacebo v7.360.0 `tone_mapping.c`, `shaders/colorspace.c`, `lp_sh_colorspace.c`, `lp_colorspace.c`):
1. **Peak detection** (`lp_sh_colorspace.c`): per-frame GPU compute pass; luma = Rec.2020 Y of the linearised RGB, PQ-encoded and 14-bit quantized; black cutoff 1 % (PQ) with `smoothstep` attenuation; `avg_pq` = mean of the per-block means, `max_y_pq` = max luma PQ (the maxRGB percentile path is bypassed — mpv's `peak_percentile` default is 0 → frame max); IIR `1-exp(-1/20)` per frame + scene hysteresis `smoothstep(0.01, 0.03, |Δavg|)`.
2. **Tone curve** (`tone_mapping.c`): ST.2094 knee pick (pivot clamped to 10–80 % of the PQ range, adaptation 0.4→1.0) then the **single-pivot polynomial spline** (`Pa` toe, `Qa`/`Qb` shoulder, `slope_tuning 1.5`, `slope_offset 0.2`, `spline_contrast 0.5`).
3. **Colour**: RGB(2020)→LMS→**IPT** (Ebner-Fairchild); the curve is applied to **I only**, chroma preserved via the hull clamp `((h-6)h+9)h`; back IPT→LMS→RGB(709), gamut-clipped.
4. **Output**: black-scaled delinearize — the target black (0.203 cd/m² = 203/1000) maps to code 0, `(x-0.001)/0.999` — then the target transfer (G22 for the window, sRGB for `--screenshot video`).
**Validation (objective, not eyeballed).** A synthetic 24-band PQ ramp (0.01→4000 cd/m², correctly tagged `bt2020nc/smpte2084`) was rendered by the installed mpv (`--vo=gpu-next`) and captured at 16 bits (window + video paths). The CPU port of the pipeline above reproduces mpv's measured codes to **mean abs 24.8/65535 = 0.1 code/255** (worst 0.4 code at 203 cd/m²) across the whole ramp — the algorithm is confirmed, not approximated. Harness (temp): `mpv_shot.mjs`, `mpv_bands.mjs`, `pngdec.mjs`, `mpv_model.py`; band clip `src/bandtest_hdr.mkv` + `gen_pq_bands.py`.

Reading: the **decode path is already at parity** — both run FFmpeg→D3D11VA→D3D11→shared NT handle→D3D12 zero-copy (REX logs `decoder surface: 3840x2176 fmt=P010 hdr=true pool=P010 copy=match`) and load the AMD VCN engine equally. mpv's extra cost is the **full-resolution peak-detection compute pass re-run every rendered frame** (73 % compute) plus the complete IPT pipeline. **Side finding — a second wallpaper engine collapses the video pipeline.** The Electron supervisor respawns its runtime the moment any runtime process dies, and the runtime refuses a second instance by named mutex, so a headless CLI run and the app fight over the desktop. Under that fight the telemetry showed `decFps` steady at 24.0 while `rendFps` fell 23.8 → 5.1 and **`reserve` went +163 ms → −3831 ms** (a 3.8-second backlog), `schedDrops` 2 → 1616, 242 late frames of ~1 s each, and the wallpaper crawled at 2–3 fps for ~90 s before snapping back. **The engine itself is fine**: with the app stopped the same clip presents exactly 24.0 fps, gapP50 41.68 ms, gapMax 43.06 ms, **zero** late-frame warnings. Filed as a P2 (fast self-healing from a negative reserve + cooperative second-instance handling).

**Crash fixed — concurrent Seek/Close aborted the runtime (FFmpeg frame-thread assert).** The audit surfaced a *flaky test*: `DecoderLifetimeTest.ConcurrentSeekCloseAndReadCompletes` failed ~1 run in 3 with `Assertion fctx->async_lock failed at libavcodec/pthread_frame.c:174` — an FFmpeg **abort**, i.e. the wallpaper runtime dies. Root cause: the software decode path runs a **frame-threaded** decoder (`thread_count = 0`), whose internal async lock is released by `avcodec_receive_frame()`, by `avcodec_flush_buffers()` (Seek) **and** by `avcodec_free_context()` (Close) — so an overlap releases it twice and trips `av_assert0` in `async_unlock()`. The overlap was reachable because `VideoPlaybackController::Close()` frees the codec context *outside* `m_decodeMutex` while a concurrent `Seek()` flushes it (a use-after-free as well). Fix: a codec-exclusion mutex inside `FfmpegVideoDecoder` (recursive — `DecodeFrame` calls `SeekInternal` for the EOF loop wrap) covering `DecodeFrame`, `Seek`/`SeekInternal`, `Flush`, `SelectStreamByResolution` and `Close`, plus a null-context guard in `SeekInternal`. Verified: **24/24** concurrent executions of the previously-flaky test (it failed ~1 in 4 rounds before), full suite **808/808**.

**Also fixed — `SpeedClockTest` was hostage to the monitor's power state.** The engine correctly auto-pauses when the OS reports the console display as off, and this box sleeps the monitor after 300 s of idle — i.e. after any multi-minute build — so the rate test read 0.0009 s instead of ~2 s. The test now holds the display awake (`SetThreadExecutionState(ES_DISPLAY_REQUIRED)`, which also wakes a sleeping monitor), waits for `Running`, and skips with the cause named if there is no live display.

**10-bit SDR output + dithering (2026-10-20).** The wallpaper now leaves the engine in the same shape mpv's window is in:

| | before | now |
|---|---|---|
| SDR back buffer | `R8G8B8A8_UNORM` (8-bit, 256 levels) | **`R10G10B10A2_UNORM`** (10-bit, 1024 levels — the exact format mpv 0.41.0's window uses) |
| output quantisation | truncation (banding) | **dither**: Interleaved Gradient Noise at one code of the output depth, added to the encoded signal |
| colour space | `RGB_FULL_G22_NONE_P709` | unchanged (the same space mpv declares) |
| HDR output | `R16G16B16A16_FLOAT` | unchanged (FP16 is not quantised, so it does not dither) |

The dither amplitude is compiled into the pixel shader per pipeline state (`TARGET_BITS` = 10 / 8 / 0) and the rule lives in `graphics/renderer/OutputDither.hpp`, pinned by `ColorPipeline.OutputDitherMatchesTheTargetDepth` — the shader and the test cannot drift. The swapchain falls back to 8-bit UNORM if a driver refuses the 10-bit buffer (at creation *and* on a later resize, and the refusal is remembered so it is not retried every refresh), and the SDR pipeline state is rebuilt when the format changes, because a PSO's RTV format must match the buffer it renders into. On an 8-bit *desktop* the DWM's own dither handles the final 10→8 step, so the visible banding is gone either way; on a 10-bit desktop (Windows 11's per-monitor "Desktop mode" setting) the engine now delivers true 10-bit.

Two things had to change to get there: the pixel shader is now split across two literals (MSVC caps a single raw string literal at 16 KB and the shader had just crossed it), and the dither rule moved out of the renderer into a testable header. Suite **809/809**.
**Housekeeping off the render thread (2026-10-20).** The display-topology probe (a DXGI output enumeration plus \GetDpiForMonitor\) used to run **inside the render thread's frame budget** and blocked it for 415 ms and 1084 ms on a contended desktop - a one-second freeze of the wallpaper, invisible in any average FPS. It now runs on a dedicated **housekeeping worker thread**: the render thread only raises a request flag and never waits, and the worker is stopped and joined before the renderer/video teardown. Measured on the clip that produced 242 late frames before: **0 late frames, 0 slow-housekeeping warnings, exactly 24.0 fps**.
**The backlog can no longer become an equilibrium (2026-10-20).** When the wallpaper fell behind the wall clock by more than a second, the pipeline used to stay there: the renderer presented the newest *due* frame, so the content advanced at the renderer's (slow) rate, the ring stayed full, the decoder stayed blocked, and the reserve sat at **−3.8 s** for ~90 s at 2–3 fps. The scheduler may now present the **newest published** frame when the backlog is deep (`FrameScheduler::Tick(targetPts, allowCatchUp)`) — the content jumps forward, the ring drains and the decoder unblocks. It is **off by default**: normally the newest published frame is *ahead* of the playhead (the decode-ahead reserve), and presenting it is exactly what made the wallpaper read as playing at 2x. Two new scheduler tests pin both halves.
**Muted audio no longer decodes (2026-10-21).** The wallpaper's audio is silent by default (the protocol `LOAD` defaults to `mute=true`) and the decode was the expensive part — measured on the 4K HEVC 10-bit + 5.1 DTS-HD MA clip: **0.7 %** of one core with no audio track, **4.5 %** decoding 5.1, and **7.7 %** decoding it for nobody to hear. While nothing can be heard (muted, or volume 0) the player now **does not decode at all** — the demuxer stops being read, so it keeps its position, and unmuting re-seeks the audio to the *video's* position before the decode resumes (the seek is request-based, so it is consumed on the audio thread and the sound comes back in sync). Muted cost: **7.7 % → 3.0 %**. The underrun counter stopped counting that deliberate silence too, so the health line reads honestly: `0 fps decoded, 33782 fps rendered, 0 underruns`.
**The tempo path no longer aliases (2026-10-21).** Changing the playback speed resamples the content frames onto the endpoint's frame count, and linear interpolation folded the spectrum back over itself there - a tone near Nyquist was attenuated, anything above it whistled. The resampler is now an 8-tap Blackman-windowed sinc with the cutoff at **0.5*min(1, 1/ratio)** cycles per source sample, so speeding the content up lowers the cutoff and filters the aliasing band out. Two unit tests pin it: a smooth signal passes through within 0.09 %, and a tone above the new Nyquist is filtered out where the linear version aliased it back. The second test caught a real bug in the first draft - the cutoff was normalised to Nyquist but used as cycles-per-sample, so it was 2x too high and the anti-aliasing was not actually happening.
**The SDR white level now comes from the OS (2026-10-21).** On an HDR display the OS knows how bright 'SDR white' should be - it is the Windows 'SDR content brightness' slider - and exposes it as a fixed-point multiplier of the 80-nit reference. The engine reads it through the display-config API (matching the DXGI output the window sits on) and uses it to scale SDR content on an HDR panel; on an SDR display the API reports nothing and the 100-nit fallback (ITU-R BT.2408) holds. The constant lane was already correct - only the value was missing.
**The on-screen mpv parity re-verified (2026-10-21) - and the capture path explained.** The 24-band PQ ramp fixture was rebuilt correctly (the clip has to be tagged FULL range: a limited-range clip makes the decoder expand the 10-bit PQ codes and the ramp then peaks at 8274 nits instead of 4000 - the engine's own peak detector now reads **4087 nits** for the 4000-nit band). Measured against the mpv model on the real screen, the engine's wallpaper matches to a **median of 1.0-1.2 codes** over the 24 bands (16 bands within +/-1.6). The bright bands read up to +18 codes high, and an A/B settled the cause: the **same** profile appears with an 8-bit swapchain, so it is not our 10-bit output - it is the **DWM mapping SDR content into an HDR framebuffer** (the display was switched to HDR 400 mid-session). mpv's window is SDR too and goes through the identical mapping, so the comparison stays fair; the tool's own note already flags that the DWM applies the display profile on the way to the screen. With the desktop in SDR the same capture lands within +/-1.6 of the model across the whole ramp.
**A/V sync, pre-sized hardware frames, and the HDR-desktop colour bug (2026-10-21).** Three fixes: (1) an **A/V sync watchdog** - the audio is clocked by the WASAPI endpoint and the video by the engine's wall clock, and nothing compared them; the watchdog measures the *change* in the audio-vs-video offset (both positions lead their playhead by a fixed amount, so the offset itself is not the error) and re-seeks the audio onto the video's position only past 250 ms, never while the output is silent (the decode is suspended then, so the audio position is frozen by design) - the decision is a pure function and is unit-tested. (2) **Pre-sized hardware frames** - the decoder now has a \get_format\ callback that allocates an \AVHWFramesContext\ at the known size, so the decoded surfaces are allocated once instead of being re-allocated (and the pool rebuilt) when the resolution changes mid-stream. (3) **HDR desktop = green/magenta wallpaper (user-reported, fixed)** - with the display in an HDR mode the DWM misread our 10-bit UNORM swapchain and every SDR wallpaper came out with the R and B channels wrong; the DXGI colour space does not reveal an HDR desktop (the DWM still presents SDR windows as G22), so the engine was on the SDR output path while the compositor composed it as HDR. The swapchain now asks the OS whether the display is in an HDR mode and uses the HDR output path there - the format the compositor expects - with the SDR white level taken from the OS.
**The parity fixture and the parity model had drifted apart (2026-10-21).** The 24-band PQ ramp is generated by `tools/color/make_bands.py` and measured against `tools/color/shader_port.py`'s `MPV_BANDS` — the list mpv 0.41.0's own 16-bit captures were taken on. Unit 22 changed the **generator's** copy of that list and left the model alone, so the fixture really did carry 500/800/1200/2000/3000 cd/m² in the upper bands while the model expected 400/600/800/1000/2000: the on-screen check then reported a **"+7…+17 code regression"** on the bright bands that the engine never had — the clip was wrong, not the renderer (the earlier "the DWM's SDR→HDR mapping lifts the highlights" reading was a red herring). The generator now **imports** `MPV_BANDS`, so the fixture, the model and the mpv reference cannot drift apart again; the clip was rebuilt (FULL range, lossless HEVC) and its band codes match the nominal values within 2.7 codes. **Measured on the real screen with the rebuilt clip: median 0.67 codes, max 3.17** (the 0.01 cd/m² band) over the 24 bands, the bright bands within 1.5 — the parity the engine was supposed to have all along.
**4K clips decode on the GPU again (2026-10-21).** The `get_format` callback pre-allocated the decode surfaces so FFmpeg would not re-allocate them when the resolution changes mid-stream — but **FFmpeg's D3D11VA decoder creates the decode texture itself** and its `pool_init()` refuses a caller-allocated context (`AVD3D11VAFramesContext.texture not set` → `Failed setup for format d3d11` → the hwaccel never initialises → **software decode**). Measured on the user's own 4K 60 fps clip: `software frame conversion (CPU upload) active decodePath=SW_BGRA8` and **14 late frames of 150–180 ms in 35 s** — a visible hitch every 2.7 s. The pre-sizing is gone; the callback only selects the hardware pixel format (and still skips chroma layouts D3D11VA cannot decode). **After:** the same clip decodes on the GPU (`decoder surface: 3840x2176 fmt=NV12 … pool=NV12`), **0 late frames**, and exactly **60.03 fps** on a 60 fps source. The A/V watchdog also stopped re-seeking the audio every 2.8 s for media with **no audio track** (the position stays 0, so the watchdog measured the whole video position as "drift"); it now stands down when the player has no audio, which removed the last ~170 ms hitch on that clip.
**The A/V drift is now visible (2026-10-21).** The sync watchdog measured the drift and acted on it, but nothing reported it: the value lived in two private atomics with no reader, so the only way to learn that the audio and the video had parted was to hear it. The drift and the correction count are now telemetry — `avSyncDriftMs` / `avSyncCorrections` in the playback and engine telemetry structs, in the runtime's `GET_STATUS` JSON, in the machine-readable `runtime-telemetry.log` line (`avDrift=…ms avCorr=…`), in the engine's telemetry panel, and in the watchdog's own log (the drift every ~4 s at debug level, a warning when it corrects). **Measured** on the PQ ramp with an AAC track (`--unmuted`): the drift holds at **-3 ms / +7 ms** with **0 corrections**. Two log-line bugs surfaced while doing this: the drift warning used **printf** placeholders (`%.0f`) inside a `fmt`-formatted logger and had been printing its own format string instead of the numbers since it was written — the decoder's "hardware frames pre-sized" line had the same defect; both are fmt-style now, and a tree-wide scan found no other printf-style log lines in the engine.
**The Catmull-Rom kernel now actually runs (2026-10-21).** The shader decides between the 16-tap kernel and the sampler's bilinear tap from the UV derivatives: `scale` is *source texels per output pixel*, so a magnified source (video smaller than the desktop) has `scale < 1`. The early-out tested the other way round (`scale <= 1.0001`), so the kernel was skipped on **every upscale** — the only case it exists for — while a minified source paid for 16 taps it did not need; the code's own comment ("1:1 or minified") already described the intended test. The early-out now tests `scale >= 1.0001`. **Measured on the 24-band ramp (1920x1080 on a 3840x2160 desktop), the same capture method before and after:** the band-edge 10-90 % transition goes from a **median 2.20 px** (bilinear) to **1.74 px**, the worst edge from 6.2 px to 2.2 px, while the on-screen parity against the mpv model is unchanged (**median 0.67 codes**) because the band interiors are flat. GPU 3D at 4K rises from 1.4-2.1 % to **~11 %** for the 16 taps and the content still plays at exactly the source rate (**25.07 fps** on a 25 fps clip, 0 late frames); a 1:1 source keeps the single exact tap, so a 4K clip on a 4K desktop pays nothing. The unit-26 claim that "a 2x bilinear upscale cannot go below 2 px, so the resampler is provably active" was wrong on both counts — 1.37 px is what bilinear measures at 2x, and the resampler was not active.
**The wallpaper is no longer upscaled with a bilinear blit (2026-10-21).** The video is drawn as one fullscreen quad, so a video smaller than the desktop was magnified by the sampler's bilinear filter - visibly soft next to mpv (whose gpu-next default is \--scale=lanczos\). The shader now resamples the **luma with a Catmull-Rom (bicubic) kernel** (the chroma keeps the bilinear tap: it is subsampled anyway, and doubling the tap count for it costs more than it shows). 16 taps, and only when the source is actually magnified - the magnification factor comes from the UV derivatives, so no extra root constants are needed (the budget is exactly 64/64 DWORDs) and a 1:1 source keeps the single exact tap. Measured on the 24-band ramp (1920x1080 on a 3840x2160 desktop): the band-edge transition is **1.37 screen px** (10-90 %, median over 9 edges) - a 2x bilinear upscale cannot go below 2 px, so the resampler is provably active. GPU 3D goes from 1.4-2 % to **8.3 %** with the taps, and the content still plays at exactly its source rate (25 fps / 30 fps measured). A true separable **Lanczos** (6 taps per axis, mpv's default) needs two passes or 36 taps in one - left as a follow-up.
**Publishing a build for testing on another machine (2026-10-21).** `npm run dist:win` (in `app/`) produces two artefacts in `app/dist-exe/`: **`Paiint-<version>-<date>.exe`** (the portable single-file build) and **`win-unpacked/`** (the folder build). Either can be copied to another PC; both carry the native runtime (`resources/bin/paiint-wallpaper-runtime.exe` plus the FFmpeg DLLs), so the engine under test is the one that was built. The packager script used to copy only the portable exe and delete the unpacked folder, which left a **stale `win-unpacked/`** from an earlier build - a tester who took the folder would have run the OLD native runtime with the new UI. It now refreshes both. Verified from the package: the shipped runtime starts standalone, reports `Back buffer: R10G10B10A2_UNORM SDR 10-bit`, `Peak-detection pipeline ready (mpv parity)` and presents at exactly the source rate (30 fps measured). Note the new second-instance guard: a second runtime on the same desktop now exits with "another wallpaper runtime already owns the desktop layer" instead of fighting for the WorkerW layer - stop the running app before launching a headless runtime for a side-by-side test.
**Hardware neutrality (audited 2026-10-21, for testing on other machines).** The engine contains **no vendor-specific code** - the only "AMD" string in the native sources is `IMAGE_FILE_MACHINE_AMD64` (the x64 unwind). Everything is plain D3D12 + D3D11VA, so NVIDIA, AMD and Intel all take the same path. What the code does is *adapt*:
- **GPU choice:** `Device.cpp` enumerates with `EnumAdapterByGpuPreference(HIGH_PERFORMANCE)`, so the OS's own GPU preference decides (a laptop with an iGPU + dGPU gets the dGPU; a desktop gets its only GPU), skips `DXGI_ADAPTER_FLAG_SOFTWARE`, probes each candidate for D3D12 support and falls back to the default adapter.
- **The interop side:** the decoder's D3D11 device is created on the **same adapter** as the D3D12 device with `D3D11_CREATE_DEVICE_VIDEO_SUPPORT | D3D11_CREATE_DEVICE_BGRA_SUPPORT` - BGRA support is exactly what NVIDIA requires for the D3D11->D3D12 shared-texture path, so the interop is already NVIDIA-correct, and putting both devices on one adapter is what makes the shared handle legal.
- **Hardware decode:** the driver is asked for its decoder profiles (`hardware decoder profiles reported by driver: N`) and a codec the driver cannot decode falls back to software decode with auto threads.
- **The 10-bit swapchain** falls back to 8-bit UNORM if a driver refuses `R10G10B10A2` (creation *and* resize), and the SDR pipeline state is rebuilt for whichever format won.
- **No audio endpoint** is not fatal: the wallpaper plays silently.
The one AMD-specific thing in the tree is a *measured driver quirk*, not a code path: on this box a **buffer->texture copy removes the device**, which the engine's pool path avoids entirely (it blits the D3D11 surface through a shared NT handle). A different driver may still behave differently, so the first run on a new machine is worth watching in `%TEMP%\REX\runtime.log`.
